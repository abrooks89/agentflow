# Data Layout — the consolidated single-root

Agentflow keeps **all** project work under one configured root, `data_root` (an
`environment.*` field; see `skills/_shared/SCHEMA.md` §1). Under that root, every project
owns a fixed subtree derived from `data_root` + the project `name` (the routing key = the
stem of a `~/.agentflow/config/projects/<name>.md` file).

There is exactly **one home per work-file kind** — no scattered spec/plan/queue/status
trees, no per-machine path sprawl. Skills address these locations by config token
(`<data_root>` + `<name>`), never by a literal path.

## The layout

The four top-level buckets are the **pillars**, and the axis between them is *who writes them*
rather than what they hold ([`ARCHITECTURE.md`](ARCHITECTURE.md), *Four pillars*). Three of them
are created by the installer. `autodoc/` is not, and nothing else creates it either — today it
exists only where a human set `environment.autodoc_root` (below) — and `design/bugs/` is not
either; the steward generates it from the tracker. Both are
marked below, because a tree drawing a directory a fresh install does not have is how a reader
concludes their install is broken.

```
<data_root>/
└── projects/
    └── <name>/
        ├── design/       # what we INTEND to build       — human-authored
        │   ├── specs/       # functional design docs        — <slug>-design.md
        │   │   ├── done/       # TERMINAL partition — a view of current_state, moved by reconcile
        │   │   └── archived/   # TERMINAL partition — closed without delivering
        │   ├── plans/       # technical plan docs           — <slug>.md   (same two partitions)
        │   ├── use-cases/   # use-case docs (traceability spine)
        │   ├── suggestions/ # harvested feature suggestions
        │   └── bugs/        # NOT scaffolded — DERIVED from the tracker by the steward
        ├── autodoc/      # what the code IS  — NOT scaffolded; /autodoc-init needs autodoc_root set first
        ├── wiki/         # what we LEARNED              — written by sessions
        │   ├── pages/       # durable pages, Karpathy-wiki style — CREATION-ONLY
        │   │   ├── done/       # terminal partition; not read by the projection
        │   │   └── archived/   # terminal partition; not read by the projection
        │   ├── hot.md       # PROJECTION over pages/ — project-wide top-N. Generated.
        │   ├── hot-<lane>.md # PROJECTION over pages/ — one per lane. Generated.
        │   ├── digest.md    # human-facing, written by the STEWARD on its sweep
        │   └── residue-baseline.json  # the residue RATCHET's recorded state. Lives here, not in
        │                    # the repo, because it is a statement about THIS data root: a repo
        │                    # copy would ship to the next install as a lie. Seeded empty at
        │                    # provision when the pillar has no pages yet (write-if-absent);
        │                    # otherwise written only on
        │                    # `agentflow.wiki residue --update-baseline`; see docs/runbooks/publish.md.
        └── status/       # orchestrator status boards         — <slug>.status.md  or  <slug>/status.md
                          # + registry.md (the Fleet Registry — the single coordination surface)
                          # + registry-log.md (the steward's cull target; never read in the hot path)
                          # + <agent>-state.md (per-agent loop state — lead-dev-state.md, jr-dev-1-state.md, …)
                          # + audit-ledger.md (auditor: one row per audited epic; already-audited filter)
                          # + audits/ (auditor: full per-pass reports — YYYY-MM-DD-<pass>.md)
                          # + workflows/ (orchestrator: baked per-wave Workflow variants — wave_group_<tag>.js; deleted at wave terminal state)
```

> **`queue/` is retired.** All per-agent loop state consolidates at
> `status/<agent>-state.md`, and shared coordination lives only in the registry.
> An `<agent>-state.md` carries that loop's continuation state across firings and
> is **single-writer**: exactly one loop writes it — its own — and
> `skills/steward/SKILL.md` puts the rule in one line ("Never write another
> lane's state file"). Reads are not so restricted: the two jr-dev skills read
> each other's state file to detect a session re-pointed between lanes. There are no per-loop questions files — questions
> are registry `## Questions` rows (see `docs/REGISTRY.md`).

> **`design/bugs/` is the one derived thing under `design/`.** Everything else here is
> human-authored; the bug files are a rendering of the issue tracker, regenerated by the
> steward (`python -m agentflow.issue_intake mirror --project <name>`) and never hand-edited.
> The issue stays the system of record, so a correction belongs on the issue — an annotation
> written into the mirror survives exactly until the next sweep. Only `index.md` and the
> CURRENT month's `closed-<YYYY-MM>.md` regenerate; earlier months are frozen, because
> regenerating a closed month can only ever rewrite history. The generated files carry a
> `generated-at` stamp that is deliberately EXCLUDED from the write-if-changed comparison:
> a reader needs to date the mirror, and a sweep that changed nothing must still leave the
> bytes alone.

`<name>` is the project routing key. `<slug>` is the epic slug (the filename stem, with any
leading `YYYY-MM-DD-` date prefix and trailing `-design` suffix stripped for identity).

## The directory is derived from the frontmatter, never the other way round

**`done/` and `archived/` are a materialized view of `current_state`.** Nothing decides where an
authored record goes: `python -m agentflow.reconcile --project <name>` walks every directory under
`design/`, reads each file's frontmatter, and moves the file to match. `done`/`shipped` file into `done/`; the rest of
`epic_survey.TERMINAL_CURRENT_STATES` (`archived`, `superseded`) file into `archived/`; everything
else lives in the bucket root, which is the point — opening `specs/` shows you what is live. On the
largest live project that is the difference between a folder of 404 files and a folder of 91: a
report-only run on it files 313 of that bucket's specs into `done/` and `archived/`.

Three things about that rule are load-bearing, and each of them was learned the hard way:

- **The frontmatter is the source and the directory is the view.** Editing `current_state` to make
  a file's location correct inverts the rule and gives you two states with no rule for which wins.
  The steward, which runs this pass (`skills/steward/SKILL.md`, domain A2), is explicitly forbidden
  from doing it. The rule runs both ways: moving an `approved-for-autonomous` spec into
  `archived/` does not withdraw its approval (it stays dispatchable, and this pass moves it back
  to the bucket root); only editing `current_state` does (`gh#233`).
- **Unplaceable is a third outcome, not an error and not a default.** A file whose `current_state`
  cannot be read is left exactly where it is and named in the report — 169 files across that same
  project's design tree are in that condition as of this writing, nearly all of them under
  `plans/grounding/`. Treating them as active would have hidden every
  one. The refusals are the part that needs a human; the moves need nobody.
- **The read side derives its globs from the same tuple the write side moves into.** Each authored
  family is three globs — the bucket root plus each of `TERMINAL_PARTITIONS` — because a terminal
  record is still a record. When the globs were single-level, every file this pass moved left the
  survey, a *finished* prerequisite read as unsatisfied, and 440 records across two projects sat
  stranded behind dependencies that were already met (`gh#122`).

The `wiki/` pillar uses the same names under a different rule, with a different mover: `pages/` is
creation-only, a page is retired by **moving** it into `pages/done/` or `pages/archived/`, and
`agentflow.wiki` skips those names at any depth so a retired page keeps its history and leaves the
projection. A retirement is routine rather than exceptional, which is why the projection refresh
sweeps its own `hot-<lane>.md` files in the same pass — a lane that loses its last live page would
otherwise keep a stale hot file that asserts its own freshness. The same move is how a page
that fails the residue ratchet (`python -m agentflow.wiki residue`) is cleared: supersede it with
a clean page, archive the dirty one, and it leaves the ratchet because the check skips these
partitions too.

## What never leaves this tree

`design/`, `autodoc/` and `wiki/` are documents, but only design specs and plans mirror to the
optional vault today (the `backlog`, `project` and `solution` skills call `vault.mirror_helper`;
nothing else does). `autodoc/` and `wiki/` are not mirrored, so a built corpus is untracked: its
pages can be re-rendered from the graph store at `<autodoc_root>/.source/graph.db`, but that store
lives inside the same tree, so deleting the tree loses both.

**`status/` never mirrors, and the reason is worth more than the rule.** A bare prohibition gets
optimised away by the next person who adds a sync client and cannot see why a folder of markdown
should be exempt. This is why: `status/` is coordination under a lock. Writes go through
`python -m agentflow.registry`, which takes a `mkdir` edit-lock, re-reads under it, edits and
releases. A file-sync client copies a file when it notices the bytes change; **it cannot see that
lock**, so it races a mutex it does not know exists — and what it carries out of the race is a
half-written registry that every loop then reads as truth, on a tree git does not cover. No skill
hands the mirror helper a `status/` path. The helper ships with the vault, not this repo, so whether
it refuses one is not checked here. The same reasoning is why nothing in `status/` is hand-edited
either.

## Who reads / writes each subdir

| Subdir | Written by | Read by |
|---|---|---|
| `design/specs/` | `refine`, `backlog` (placeholder specs), `dev-manager` (decisions) | `project`, `solution`, `choose-next`, disk epic-survey (Pass 1) |
| `design/plans/` | `solution` (via vendored `writing-plans`) | `project`, `orchestrator`, disk epic-survey (Pass 2) |
| `status/` | `orchestrator` (status boards); all seven loops write their owned `registry.md` rows (ownership rules: `docs/REGISTRY.md`); the `steward` culls it → `registry-log.md`; each loop writes only its own `<agent>-state.md`; `auditor` writes `audit-ledger.md` + `audits/YYYY-MM-DD-<pass>.md`; `orchestrator` bakes `workflows/wave_group_<tag>.js` per wave (`wave_dispatch.wave_script_dir`) and removes it on the reconcile wake — runtime state carrying the project's absolute paths, never written into the suite tree | all seven loops (whole-registry read at every state-bearing firing), `choose-next`, disk epic-survey (Pass 3) |
| `design/use-cases/` | `refine` / `solution` / autodoc (Phase-4 traceability) | traceability greps (`grep UC-####`) |
| `design/bugs/` | `steward` ONLY, and only by regenerating it from the tracker (domain M) — never by hand, by any loop | humans reading the board; `fleet_report` reads the TRACKER, not these files |

> **Fleet Registry** (`status/registry.md`) — the single coordination surface all seven loops
> share (binding schema, firing contract, question lifecycle: `docs/REGISTRY.md`). Every loop
> reads the WHOLE registry at every state-bearing firing (lock-free) and writes only the rows
> it owns under one mkdir edit-lock (`<lock_dir>/<project.name>-registry.lock`, stale >5 min =
> breakable); the `steward` culls closed entries out to `registry-log.md` verbatim (E-0220 moved
> `cull`, `reap`, `stand-down` and `repair` there, and the CLI refuses all four to anyone else).
> The registry carries the `## Queue` lanes (`lead` / `jr-dev-1` / `jr-dev-2` / `jr-dev-3` —
> `registry.LANES`), the deploy lock,
> agent-to-agent Notes, `## Questions` (the only path from any agent to the human),
> `## Blockers`, and `## Directives`. It is the single shared coordination surface —
> questions are registry rows, never per-loop side files.

> **Carved-from-issue specs** (under `design/specs/`) — a spec that `dev-manager`'s issue intake
> (§3.4) carves from a tracker issue carries the tracker ref in its frontmatter as
> `source: gh#N` (the value may name several refs, e.g. `source: "gh#12, gh#40"`; the `gh#N`
> tokens are what matter). `agentflow.issue_intake.spec_linked_issue_numbers` greps that
> field across `design/specs/` so the intake skips issues already carved, without needing a label
> round-trip to the tracker. This is a frontmatter convention on the existing `source` key —
> no schema change and no new file.

> **Auditor artifacts** (under `status/`) — the `auditor` loop writes two things here:
> `audit-ledger.md` (one row per audited epic — slug, date, verdict counts, gap epics filed;
> this row is also the already-audited filter that stops re-auditing) and `audits/` (the full
> per-pass reports, `YYYY-MM-DD-<pass>.md`). The drafted gap epics the auditor files land in
> `design/specs/` (where `dev-manager` finds them natively); on the registry the auditor keeps only
> its own `## Agents` row current (and raises `waiting`/`advisory` Question rows — never
> `halted`) — the ledger is the audit record of note.

## Backups

A backup is a file kind this subtree never named. Compare the two neighbours it most resembles:
`registry-log.md` has a home (`status/`) and an owner (the registry module appends it), and
`status/audits/` has both as well (the auditor writes it, and its retention is its own). A
backup had neither, and nothing here ever removed one. Every loop takes a `.bak` before a
programmatic edit — `skills/dev-manager/SKILL.md` states the rule and the reason — because
**`data_root` is not git-managed and a bad edit here is unrecoverable.** That rule stays. What
follows is the bound on it, not a softening of it.

**The format is defined in code, once: `agentflow.backups`.** Read the shape there. It is
deliberately not written out here or in the SKILL.md files this repo has converted — a filename
pattern copied into prose is a second definition nothing keeps honest, and a tree full of
hand-invented suffixes is what that costs. To take a backup, call `agentflow.backups.take_backup`
(or `python -m agentflow.backups new <path> --firing <id> --copy`) rather than composing a name:
it claims the name atomically, which composing one by hand does not, then copies the file in
and verifies the copy is non-empty and identical, removing its claim and exiting 2 if it is not.
`next_backup_path` and a bare `new` only CLAIM the name and leave it EMPTY; they are for a
caller that hands the claim to its own writer (as `autodoc-update` does with its manifest) and
then checks it. A seat that followed "claim the name" as the whole rule held a zero-byte file it
believed was a backup (gh#712). A seat with no firing counter (`dev-manager`, `autodoc-update`)
uses any per-run epoch seconds (`date -u +%s`) for the firing number; the claim is exclusive and
timestamped, so the number need not be reused across a run.

**"Converted" is not "the whole tree".** `dev-manager` and `steward` point at the module and a
test holds them to it; `skills/autodoc-update/SKILL.md` claims its manifest backup from the
module too (gh#184). The one hand-written backup name left is `skills/autodoc-init/SKILL.md`'s
`${AUTODOC}.pre-store.bak` (or a UTC-stamped sibling of it, on a re-init that finds that name taken),
a directory the reaper does not reach by design. Read this section
as the rule, not as a finished sweep.

Two properties of the format are worth preserving. The timestamp is fixed-width and UTC, so a
lexical sort of the names is a chronological one — for `ls`, for a glob, and for a human reading
a directory. **No shipped code depends on that**: the reaper orders a group by `st_mtime`,
because a group mixes canonical names with legacy ones that carry no parseable time at all. The
second property is load-bearing in code: **the tail goes after the primary's extension, never
before it** — `## Discovery` below globs `*.md`, so a backup ending in `.md` would enter the
queue as a phantom epic, once for every backup ever taken.

| Written by | Removed by |
|---|---|
| every loop, before any programmatic edit under `<data_root>` | `steward` (domain A3), report-only — `python -m agentflow.backups reap` |

The writer and the reaper are deliberately different components. `dev-manager` writes the most
backups and cannot own their removal: it has no self-wake and exists only while a human is
sitting in it, and retention that runs only when someone sits down has no owner at all. The
steward already runs the same shape (`agentflow.reconcile`) against the same tree on every wake.

> **The reaper keeps the newest `KEEP_DEFAULT` backups of each file, and refuses outright any
> group it cannot prove is safe.** It
> groups by (directory, primary filename), so one file's depth can never spill onto another's.
> Retention is count-based, which bounds the depth **per file** — the steady state is
> (primaries × keep) and grows as files are written. It does not bound the size of the tree;
> that would need an age rule or an archive-on-close rule, and neither exists.
>
> **A zero-byte backup never holds a retention slot while a non-empty one exists** (gh#712). An
> empty member is an abandoned claim, not a copy, and it is usually the newest file in its group,
> so ranking by age alone let a run of empty claims push the one real backup out of the keep
> window and delete it. The keep window is filled from the non-empty members, the empty ones
> are removed, and so the newest non-empty backup of a file is never reaped. A group whose
> members are all empty ranks by age as before: there is nothing in it to protect.
>
> **A group whose primary is missing or zero-length is a NO-OP.** Those backups are the only
> surviving copy of that file, and a retention rule that eats the last copy is the incident the
> backup rule was improvised to survive in the first place. Such a group is left untouched and
> named in the report as a refusal — a third outcome, like `reconcile`'s unplaceable files, not
> an error and not a default. The refusals are the part that needs a human; the removals are
> mechanical.
>
> **A refusal marked `MOVED` is the exception, and it is a caption rather than a verdict.** Most
> refusals in a mature tree are not last copies at all: the primary was renamed, or relocated
> into `done/` by a pre-gh#288 `reconcile`, and a live file elsewhere carries the same spec
> `slug:`. When exactly one live file does, the report says so and names it. Measured on this
> tree the day it shipped: 68 refusals, 58 captioned, 10 left unexplained. Nothing about the
> sweep changes - the group is still refused, every backup is still kept, and the exit code is
> still 1 - but the human-facing call-list shrinks to the entries that actually need judgement.
>
> **Three things the caption deliberately will not do.** It will not resolve an ambiguous slug:
> the spec and plan pillars share slugs by design, 83 slugs in this tree are held by more than
> one live file, and guessing a winner would assert a lineage nobody checked. It will not read a
> `slug:` outside the frontmatter block, because body prose keeps advertising an identity the
> frontmatter has already moved past - the one example the epic's own spec named by hand turned
> out to be exactly that trap. And an UNCAPTIONED refusal is not evidence of a last copy; it
> means only that no unique live slug was found. Retention still does not know the spec layout:
> the CLI hands `plan_reap` a resolver, and the rule itself stays ignorant of what a spec is.
>
> **Report-only is the default, in the API and not just the CLI.** `plan_reap` is pure and
> returns a plan; `apply_plan` executes an already-computed one and reports per file what did
> and did not go. Deleting under a tree git cannot contradict is the one operation where doing
> nothing must not depend on every code path honouring a flag.
>
> **The periodic sweep is a bare `reap`, over all of `<data_root>`.** `--project <name>`
> narrows to `projects/<name>/` and therefore cannot see `archive/`, where a large share of the
> refusal groups live — including archived project trees whose primaries are gone entirely, so
> every backup there is a last copy. Scoping the routine sweep by project would hide exactly
> the groups the report exists to surface. `--project` stays for the narrow question.
>
> **The exit code is the machine-readable answer.** `0` = bounded (nothing pending, nothing
> refused); `1` = not bounded (removals pending, or a refusal standing); `2` = bad invocation,
> including a `--project` whose directory does not exist and a `--keep` below 1. A typo must
> not read as a clean tree.

## Discovery

The disk epic-survey (`agentflow.epic_survey.survey_epics`, which replaced an earlier HTTP
work-discovery service) globs this layout by default:

- Pass 1 (`design/specs/`): `projects/*/design/specs/*.md`, `projects/*/design/specs/done/*.md`,
  `projects/*/design/specs/archived/*.md`  → `speccing` (unless `current_state` overrides)
- Pass 2 (`design/plans/`): `projects/*/design/plans/*.md`, `projects/*/design/plans/done/*.md`,
  `projects/*/design/plans/archived/*.md`  → `planning`, promoted over any spec record
- Pass 3 (`status/`): `projects/*/status`  → `done` / an ended status (`abandoned`, `failed`,
  `done_on_hold`) / `running` / `unrecognised-board-status` (status.md always wins). A `status:`
  outside the board vocabulary is never guessed at, and a slug keyed by more than one board reads
  `duplicate-status-boards`; both are refused, neither done nor selectable, until the board is
  fixed or one remains

Glob patterns come from config (`SurveyPatterns`), so the layout is a config default, not a
hardcode. The defaults describe exactly the subtree above. The spec and plan globs are not
written out by hand: `epic_survey._bucket_globs` derives them as the bucket root plus one glob per
entry of `epic_survey.TERMINAL_PARTITIONS`, so the lists above are that tuple's current output.

## Scaffolding

`install/provision.py` (final step) creates `<data_root>/projects/` and, for every configured
project, the **eight** directories in `DATA_SUBTREE_DIRS`:

```
design/specs   design/plans   design/use-cases   design/suggestions
status         wiki/pages     wiki/pages/done    wiki/pages/archived
```

It then seeds `status/registry.md` from `templates/registry.md` (the `<project>` placeholder
replaced with the project name) and seeds `design/use-cases/` with `registry.jsonl`, `.counter`
and `domains.md`. It is idempotent (`exist_ok` + write-if-absent — a live registry is never
clobbered) — it never deletes or overwrites — so re-running after adding a project profile
materializes that project's subtree without touching existing work. The `install` skill runs this
as part of onboarding.

**Two directories drawn above are deliberately absent from that list**, and a fresh install will
not have them:

- **`autodoc/`** — **nothing creates this directory.** Not the installer, and not `/autodoc-init`
  either: that skill resolves its root through `agentflow.config.resolve_autodoc_root` and exits
  with `SystemExit` when none resolves, and the `mkdir` that would create the directory runs after
  that check. On a fresh install with no `autodoc_root` set anywhere, running `/autodoc-init` exits
  instead of scaffolding anything — so the pillar exists exactly where a human set an
  `autodoc_root`, in the project profile or in `environment.md`.
  `resolve_autodoc_root`, which `doctor`, the use-case touchpoint tools, `/autodoc-init`,
  `/autodoc-update` and `graph-query` use, ranks the
  project's own `autodoc_root` override first, then the machine-level `environment.autodoc_root`,
  then the derived `<data_root>/projects/<name>/autodoc` **only if that directory already exists** —
  otherwise there is no autodoc root, which is the correct fresh-install state and what `doctor`
  reports. The middle term is the one to watch, because it is **machine-level**: one value covers
  the whole box. A project skips it once the corpus there has a `.manifest.json` naming a different
  project, and falls through to its derived path or to no root; before that first build nothing
  records an owner, so every project without an override resolves to that single directory and
  `doctor` prints `ok`.
  Prefer the per-project override; the path that first builds the corpus honours it too.
- **`design/bugs/`** — regenerated from the issue tracker by the steward (above). It appears the
  first time that sweep runs against a project with a tracker configured.

## Migration — mapping a scattered setup in

> `docs/runbooks/2026-09-01-three-pillar-layout-migration.sh` is the one-time script that moved
> the single machine which had the older bucket names onto this layout. It is kept as a record of
> what was done and is **not shipped code** — it names buckets this layout no longer has, and no
> install performs it. A new install starts here.

An older setup kept work files spread across separate trees (a specs directory, a plans
directory, a loop/queue directory, and status boards written next to plans). Map them onto the
single root as follows:

| Old (scattered) | New (single root) |
|---|---|
| `<specs-dir>/<slug>-design.md` | `<data_root>/projects/<name>/design/specs/<slug>-design.md` |
| `<plans-dir>/<slug>.md` | `<data_root>/projects/<name>/design/plans/<slug>.md` |
| status board written beside the plan (`<plans-dir>/<slug>.status.md`) | `<data_root>/projects/<name>/status/<slug>.status.md` |
| per-builder loop state files | `<data_root>/projects/<name>/status/<agent>-state.md` |
| agent questions | registry `## Questions` rows (`docs/REGISTRY.md`) |
| shared queue (lanes / deploy lock / notes) | `<data_root>/projects/<name>/status/registry.md` `## Queue` |
| (new in Phase 4) use-case docs | `<data_root>/projects/<name>/design/use-cases/` |

Migration steps:

1. Pick `data_root` and record it in `environment.md`.
2. For each project, create `<data_root>/projects/<name>/{design/{specs,plans,use-cases,suggestions},status,wiki/pages,wiki/pages/done,wiki/pages/archived}/`
   (or run `install/provision.py`, which scaffolds them and seeds the registry).
3. Move each existing file to its new home per the table above, deriving `<name>` from the
   file's `project:` frontmatter (or your project routing).
4. Confirm discovery: `survey_epics(data_root, mtime_cutoff_iso)` should return the same epics
   (project-wide, as a migration check. A BUILDER always passes `project=<name>` so it sees only
   its own subtree; dev-manager / choose-next / backlog deliberately stay project-wide.)
   it did before — the layout changed, the behavior did not.

The consolidation is a **path change only**. The survey, the status-board data contract, and
every skill's procedure are unchanged; only where files live is different.
